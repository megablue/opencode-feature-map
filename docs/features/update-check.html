The update check — one toast a day when a newer version is published

Status: shipped (0.3.0) · Read when: changing src/update.ts, src/config.ts, src/tui.ts, the tui.js install shim, or the updateCheck switch

What it does

  • Loads a second entrypoint, tui, beside the server plugin. It is the only half that can put something in front of a person: the terminal context has a toast, the server context does not.
  • Once a day, reads the published package.json from the default branch, compares its version with the installed copy's, and — when the published one is newer — shows one info toast for 10 seconds: 0.3.0 is available (installed 0.2.0) - git pull && npm run plugin:install.
  • Toasts a release once. The announced version is recorded, so the same answer is silent until a newer one appears; skipping several releases still yields one toast.
  • Fails silently. A dead network, a non-OK response or a body that is not a manifest shows nothing and is not an error; the attempt is stamped and retried the next day rather than on every idle turn.
  • Never blocks. The request carries a 4-second timeout, runs after setup and on session.idle, is single-flight, and contributes nothing to a model request.
  • Switched off by { "updateCheck": false } — in ~/.config/opencode/feature-map.json, or in the plugin's options. Read once at setup, before the request: the switch stops the network call, not only the toast. The plugin never writes that file.

  • test/update.test.mjs (the rules, the switch, the toast over a fake context) and test/install.test.mjs (the shim is shipped).

How & why

A second entrypoint, because the server half cannot notify

The host resolves <plugin-root>/tui for the terminal half the way it resolves <plugin-root>/server for the other one, and package.json exports ./tui for a by-name install. The host's define is the identity function, so src/tui.ts exports a bare { id, setup } and imports none of the TUI peers (@opentui/*, solid-js) — a plugin whose server half is all there is still loads its TUI half where a toast exists.

Pure rules, a thin wrapper, durable state

src/update.ts takes a version pair, a clock reading and a manifest body as arguments, so the numeric comparison (0.2.9 is older than 0.2.10) and the repeat rule are pinned without a network or a clock. src/tui.ts owns the three things that are not pure: Date.now(), fetch and ui.toast.show.

The record lives in the host's store under update: { checkedAt, latest, notified }. The host guarantees it persists and stays in sync across terminal instances. A host that cannot provide storage gets an in-memory stand-in: the check still runs, it just toasts again on the next start, because the record only keeps the feature quiet and is not the feature.

Why a file rather than only options, and the traps

The plugin options reach the server half; the check runs in the terminal process, and a user should be able to switch it off without editing the plugins array. So feature-map.json sits beside opencode.json and both switches must allow the check. The rule is the host's for booleans: only an explicit false disables; missing, empty, malformed and any other value mean on.

The installed version is read from the shipped package.json (dist/update.js → ../package.json), never from git — an installed copy has no history. A failed attempt is stamped on purpose: without that, a machine with no network would retry on every idle turn. And the install wipes the target before copying, so the tui.js shim is re-created by the same command that repairs everything else; without it the terminal half is simply absent, with no log line — a missing TUI half is legal.

Tests that pin it

test/update.test.mjs: the config file sits beside opencode.json, and the environment can move it, only an explicit updateCheck:false turns the check off, a missing, empty or malformed file leaves the check on, versions compare numerically, segment by segment, a check is due once a day, and after a failed one, a manifest body yields its version or nothing, one toast per release, and none for the version already installed, the toast says what is available, what is loaded and how to update, the version this build carries is the version the package ships, the TUI half toasts a newer version once, and remembers that it did, an idle turn runs the same check, and the teardown removes it, the check stays silent when there is nothing newer, updateCheck:false means no request and no toast, a failed fetch is not news: it is stamped, silent, and retried tomorrow, a malformed manifest body is treated as no answer, the TUI half is a complete definition on its own, and its switch also reads options, a host without storage or a toast still checks and does not throw.

test/install.test.mjs: installs the built package: the manifest, the built output and the data (the ./tui export and dist/tui.js), wipes the target first, so a stale flattened install cannot outlive it (the tui.js shim).

No test reaches the network: each one replaces globalThis.fetch for the length of its body and points OPENCODE_CONFIG_DIR at a temporary directory.
