opencode-feature-map — features map

Read this before touching code: find the area, then open only the one or two feature docs it points at.

Read order: HANDOFF.md (current state) → this index → the page for your area → the code. docs/SPEC.html is user-visible behavior (its .md is a pointer); AGENTS.md is process and hard rules; the docs below are the map, the mechanism and the traps.

Keep this map true in the same commit as the change. Before staging a commit, update the feature doc(s) for whatever you changed, and add a row here if the doc is new. User-visible behavior also updates docs/SPEC.html in the same commit; a docs-only follow-up commit is the one that gets skipped. Pure refactors with no behavior, mechanism, config or test change need no edit.

This map is written in HTML: index.html is the index and each row links one page. A legacy README.md map is still read, and feature_map_upgrade converts one without deleting its .md files.

The index is the entry point, not a glob: pages may live in subdirectories as well as at the top level, so docs/features/*.html alone misses them. Follow the row's link.

Page format

A feature page is an HTML document with an h1 title, a p class="status" line and one section per heading. The headings are the retrieval unit: the tool returns one section at a time, so a section is what a later session reads on its own.

<h1><Feature> — <one-line summary></h1>
<p class="status">Status: shipped (vX.Y) · Read when: <trigger></p>

<section id="what-it-does">
  <h2>What it does</h2>
  <ul><li>3–6 bullets; link <code>docs/SPEC.md</code> for the user-visible detail.</li></ul>
</section>

<section id="map">
  <h2>Map</h2>
  <p>Files, types, functions and test names — the anti-hunting payload. Names, never line numbers (they rot).</p>
</section>

<section id="how-why">
  <h2>How & why</h2>
  <p>The mechanism, the invariants and the traps: cause and effect, not a retelling of the bug that produced the rule.</p>
</section>

<section id="config-keys-ui">
  <h2>Config keys / UI</h2>
  <table>…</table>
</section>

<section id="tests-that-pin-it">
  <h2>Tests that pin it</h2>
  <p>Test names — run these first when touching the area.</p>
</section>

<section id="related">
  <h2>Related</h2>
  <ul><li>Links to the other feature pages.</li></ul>
</section>

A code-shaped block is pseudocode and the default: <pre class="pseudo">. Use <pre class="verbatim" data-why="…"> only when the exact bytes must survive, and say why — a verbatim block with no reason is how a copied block escapes review. A graph is <pre class="mermaid">: the browser draws it and the tool hands an agent the edge list.

probe fails → backoff doubles → retry after ceiling → surface the error

Keep a page 60–200 lines and split past ~250, and keep a section under about two kilobytes: a section is what a later reader asks for by name, and one that outgrew a single read has to be split with h3 before it can be handed over whole. No sentence lives in two docs: docs/SPEC.html is behavior, a feature page is map/mechanism/traps, AGENTS.md is process.
